================================================================================
KEY FINDINGS
================================================================================

DATABASE STRUCTURE:
  - 13 tables across 4 categories (Auth, Content, Activity, System)
  - PostgreSQL with Prisma ORM
  - Supabase for authentication (JWT-based)
  - Two user ID fields: User.id (primary) and supabaseUserId (auth reference)

DATA CLASSIFICATION:

  PUBLIC DATA (Anonymous readable):
    - City (380+ cities with ranks)
    - Plan (10,000+ plans with weekly updates)
    - GroupFlow (curated experience flows)
    - AppConfig (system configuration)

  USER-SPECIFIC DATA (Authenticated only):
    - SavedCity (1:N relationship, isolated per user)
    - ViewedCity (1:N relationship, with analytics)
    - SearchedCity (search history tracking)
    - User profile (personal information)
    - Subscription (billing & entitlements)

  SYSTEM DATA (Admin/Service only):
    - WeeklyRefreshLog (content refresh tracking)
    - AIAgentLog (AI generation logs)
    - DailyRefreshLog (daily operations)

AUTHENTICATION:
  - Supabase Auth (JWT tokens)
  - JWT.sub = supabaseUserId (UUID)
  - Backend verifies JWT and loads User from database
  - Supports Email, Google, Apple Sign-In

API PATTERNS:
  - 50+ endpoints across 5 main routes
  - Mixed public/authenticated endpoints
  - Application-level authorization currently
  - Tier-based entitlements (FREE vs PRO)

================================================================================
RLS REQUIREMENTS MATRIX
================================================================================

PRIORITY 1 - CRITICAL (User Isolation):
  ✓ User table          - Authenticate users can read/update own record
  ✓ Subscription table  - Users can read own subscription
  ✓ SavedCity table     - Users can CRUD own saved cities
  ✓ ViewedCity table    - Users can CRUD own view history
  ✓ SearchedCity table  - Users can CRUD own search history

PRIORITY 2 - HIGH (Admin Protection):
  ✓ City table          - Public read, admin write
  ✓ Plan table          - Public read, admin write
  ✓ GroupFlow table     - Public read, admin write
  ✓ System tables       - Admin/service only

PRIORITY 3 - MEDIUM (Optimization):
  ✓ Index optimization  - Add indexes to support RLS filters
  ✓ Helper functions    - Create utility functions for policy logic
  ✓ Performance tuning  - Monitor and optimize RLS overhead

================================================================================
IMPLEMENTATION REQUIREMENTS
================================================================================

HELPER FUNCTIONS (2 required):
  1. get_user_id_from_auth()      - Map JWT to database user ID
  2. is_admin()                   - Check admin role from JWT claims

POLICIES NEEDED: 37 total
  - User table:         6 policies
  - Subscription:       5 policies
  - SavedCity:          5 policies
  - ViewedCity:         5 policies
  - SearchedCity:       4 policies
  - Public tables:      4 policies per table × 4 tables
  - System tables:      3 policies per table × 3 tables

INDEXES NEEDED: 12
  - User: supabaseUserId lookup
  - SavedCity: userId + userId,cityId
  - ViewedCity: userId + userId,lastViewedAt
  - SearchedCity: userId + userId,searchedAt
  - Subscription: supabaseUserId lookup

DATABASE ROLES:
  - authenticated   - Users with valid JWT
  - anon           - Anonymous/public access
  - service_role   - Backend service operations

CUSTOM JWT CLAIM:
  - Need "role" claim for admin detection
  - Set via Supabase Dashboard or webhook

================================================================================
ARCHITECTURAL IMPACT
================================================================================

CURRENT STATE:
  Client → Express Backend → Prisma ORM → PostgreSQL
              ↓
         Authorization middleware enforces req.user.id filtering
         Subscription checks for entitlements
         Tier-based access control

AFTER RLS:
  Two architectures supported:
  
  Option A: Keep backend (recommended initially)
    Client → Express Backend → Prisma → PostgreSQL (RLS enforced)
    Benefits: Minimal changes, dual enforcement, gradual migration
  
  Option B: Direct client access (future)
    Client → Supabase Client → PostgreSQL (RLS enforced)
    Benefits: Faster, fewer API calls, real-time subscriptions
